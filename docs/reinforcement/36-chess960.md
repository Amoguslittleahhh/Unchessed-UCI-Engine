# 36 — Chess960 castling representation

**Investigation ID:** `36-chess960`
**Tier:** 1 research and verification only
**Repository/branch:** `/home/ubuntu/Unchessed-UCI-Engine`, `manus/research-facilities`
**Scope:** Verify the claimed absence and any partial/non-core state of Chess960 castling support; run cheap real FEN/UCI and move-generation probes where feasible; research UCI and FIDE semantics; make no implementation, default, training, match, commit, or push.

## Executive summary

The fresh scan confirms that Unchessed does **not** implement Chess960 castling representation. The core board model has four fixed orthodox-rights bits (`WK`, `WQ`, `BK`, `BQ`), the FEN parser accepts only `KQkq` (or `-`), move generation assumes kings start on e1/e8 and emits only e1-g1/e1-c1/e8-g8/e8-c8 castling moves, and move application has hard-coded orthodox rook destinations. The UCI option listing has no `UCI_Chess960` option. A repository-wide targeted scan found no `Chess960`, `chess960`, `FRC`, or `UCI_Chess960` implementation or design artifact in source/non-build files. The only apparent “partial work” is the ordinary castling machinery itself; it is not generalized and cannot represent Chess960 rook files.

The release binary provided useful negative real-world evidence: it advertises no `UCI_Chess960`; a Chess960-style Shredder-FEN rights field (`AHah`) is rejected; and a Chess960-like board supplied with orthodox `KQkq` rights is interpreted using orthodox assumptions rather than Chess960 semantics. The normal orthodox FEN probe completed, although the engine chose captures rather than castling in that material position, so it does not prove a castling move was generated. Cargo source tests/builds could not run because the installed Cargo 1.75 rejects the checked-in lockfile version 4. This is an environment limitation, not a positive test result.

**Recommendation:** defer implementation. Keep Chess960 as a separately scoped future protocol/representation project. It is reasonable to retain “full validation” as **Tier 3** when validation means a production-ready variant path plus GUI/engine interoperability and game-strength/regression evidence. A smaller default-preserving parser/movegen correctness prototype could be a future Tier 2 project, but no Tier 2 or Tier 3 work should begin under this report.

## Authoritative semantics and interoperability

The [FIDE Handbook, Guidelines II, Chess960 rules](https://handbook.fide.com/chapter/e012023) states that castling may move both king and rook and describes double-move, transposition, king-move-only, and rook-move-only cases. It requires that after c-side castling the king and rook finish on c1/d1 (or c8/d8), and after g-side castling they finish on g1/f1 (or g8/f8). It also says that the paths of both king and rook must be vacant except for those two pieces and notes that squares such as a/b/e (c-side) or e/h (g-side) may remain occupied where orthodox assumptions would differ. Consequently, a correct implementation needs the actual king square, the selected rook's starting file, independent path/attack checks, and a compound relocation operation; it cannot infer legality from only KQkq and e-file assumptions.

The [official Stockfish UCI documentation](https://official-stockfish.github.io/docs/stockfish-wiki/UCI-Protocol-and-Stockfish-Commands.html) lists `UCI_Chess960` as a check option, default false, handled by the GUI, that switches Stockfish to Chess960. Stockfish's authoritative [issue #2405](https://github.com/official-stockfish/Stockfish/issues/2405) records the interoperability convention: in Chess960 UCI notation, castling is encoded as the king moving to/capturing the castling rook's square (for example `f1h1`), because a king move such as `f1g1` is otherwise ambiguous between a normal king move and castling. The issue also explicitly notes that with Chess960 enabled, `f1h1` identifies castling, whereas `f1g1` is not the castling encoding in that example.

These sources establish the protocol/rules target. They do **not** establish that Unchessed currently supports it, nor do they provide an Elo expectation for this engine.

## What a future implementation would need (not implemented)

A future Tier 2 design/prototype would need a variant-aware castling-rights representation retaining the eligible rook square/file for each side and flank, FEN parsing/serialization for the chosen interoperability convention, and a UCI option with a documented lifecycle (set before `position`, as in Stockfish practice). Move generation must locate the king and rook, validate both paths and attacked king transit/final squares under FIDE rules, and emit a canonical internal compound move. Move application, undo, hashing, rights invalidation, book move matching, policy indexing, NNUE castling features, repetition state, and UCI PV/bestmove formatting all need coordinated treatment. Tests should cover all 960 starting arrays and the degenerate king-move-only, rook-move-only, and transposition cases, plus captures/rights loss, checks, blocked paths, attacked transit squares, FEN round trips, and UCI round trips.

Full validation may remain Tier 3 because protocol correctness is only one layer. Production validation requires cross-engine/GUI interoperability over representative Chess960 positions, exhaustive or broad legal-move and make/undo checks, variant perft/reference comparisons, long-running game stability, and—if the feature is intended as a playing-strength capability—incumbent-protected paired games. Chess960 changes move encoding, state hashing, book/policy behavior, and search/evaluation distributions simultaneously. A fixed-position test can expose legality and serialization bugs but cannot establish strength, robustness across GUIs, or safe default behavior. No such Tier 3 validation was started here.

## Recommendation and status

**Defer implementation.** The evidence supports a real representation/protocol gap, not an overlooked feature. If Chess960 is a product requirement, first authorize a narrow, default-off Tier 2 correctness prototype with a written notation/FEN contract and reference-position tests. Do not change orthodox defaults or claim support until parser, make/undo, legal generation, hashing, UCI round-trip, and external reference comparisons pass. Only then should a separately approved Tier 3 interoperability and paired-game validation plan be considered. The Cargo toolchain mismatch should be resolved in an environment/setup task rather than by silently changing the lockfile for this investigation.
